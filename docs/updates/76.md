# Intent of the change

Give every OpenBot client one authenticated owner profile instead of reconstructing account labels from an email address.

- Return a required display name plus optional email, avatar, organization, and workspace context.
- Keep token verification authoritative for session validity.
- Fall back to the verified principal when optional provider profile enrichment fails.
- Preserve the same browser cookie, bearer token, refresh, logout, and origin checks.

# Architecture changes

The auth provider may enrich a verified principal, while the control service remains the only surface that exposes the normalized session contract to clients.

```mermaid
flowchart LR
  C[Web mobile desktop] --> S[/auth/session]
  S --> V[Verify access token]
  V --> P[Owner principal]
  V --> A[Optional provider account lookup]
  P --> N[Normalized owner profile]
  A --> N
  N --> R[Shared client-runtime schema]
```

- `AuthProvider.account` is optional and receives the already-authenticated access token and principal.
- The Tilde adapter maps identity, organization, and team data into provider-neutral owner context.
- The control service catches account-enrichment failures without weakening token verification.
- `@tryopenbot/client-runtime` validates one shared response shape for every renderer.

# Summarized package changes

- `@tryopenbot/auth-provider`: adds `OwnerAccount`, `OwnerAccountContext`, and optional account enrichment; the Tilde adapter implements it.
- `@tryopenbot/control-service`: enriches `/auth/session`, disables caching, and retains verified-principal fallback behavior.
- `@tryopenbot/client-runtime`: extends the authenticated user contract with display and workspace fields.
- `@tryopenbot/desktop`: updates bearer-session parsing coverage for the required display name.
- Control-service E2E fixture: supplies representative owner, organization, and workspace context for shared browser workflows.
- Changeset: records the additive public session API across the fixed package group.
- Validation: 19 focused auth and desktop tests passed. After rebasing onto merged PR 75 and updating shared session fixtures, `pnpm check` passed with 36 upstream warnings and no errors. The complete reconciled branch passed build and browser checks.

# Critical to apply to forks

no

The provider hook and response fields are additive, existing token/cookie behavior is unchanged, and custom auth providers may omit `account`. Forks with a custom direct consumer of `/auth/session` should accept the required `user.name` field and may render the optional `avatar_url`, `organization`, and `workspace` fields.

No secret, environment name, provider identifier, deployment topology, HTTP route, ConnectRPC contract, persisted state, or configuration ownership changes. After merging, customized forks should run their auth-provider, control-service, and client contract tests.
